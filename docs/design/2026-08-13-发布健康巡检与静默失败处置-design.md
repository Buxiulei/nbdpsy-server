# 发布健康巡检与静默失败处置（0.25.0）

- 日期：2026-08-13
- 状态：设计稿，待内容运营评审
- 来源：老板需求「每个笔记发布后持续关注审核状态，发布中还是没曝光、别的账号互动不了，就删除重新发布」+「审核通过了才开始触发互动任务，互动不了要及时反馈」
- 实证基础：2026-08-13 全天 RCA（4 篇静默失败处置、A/B 两型分类、李冠阳天然实验）

## 0. 判据自审表（先读这节）

今天所有故障归结为一句：**判据与被判对象之间隔了一层代理**（health 拿"下游依赖可用"代理"调用方进得来"、dedupe 拿"键已落库"代理"消息已送达"、metrics 代理台账、covered 增量代理消化速率、引用 toast 代理可见性）。代理在大多数时候是对的，只在与本体分岔的那一刻失效——而那一刻通常正是出事的时候。

**本设计每个判据都必须在此登记：它代理的是什么、什么可观测条件下会失效、失效时怎么办。**

| 判据 | 真正想知道的 | 代理失效的可观测条件 | 失效时的行为 |
|---|---|---|---|
| **探针放行互动**（闸门角色） | 这篇能被别的号看到 | 该账号**合格对照候选数 = 0**（可数）；或对照本身出问题 | **降级放行**（宁可白跑 7 次会话，见 §2.4）——误判代价只是一轮会话，而不放行的代价是**该篇永久零互动且无任何机制会回头补它** |
| **探针触发处置**（诊断角色） | 这篇确实不可达 | 无合格对照 / 单号证词 / 列表未穷尽 | **不处置**（宁可漏处置）——删错不可逆。`low_confidence` 结论一律不得进确诊、不得打 `unreachable_at`、不得触发删重发 |
| **同一页**里对照笔记可见而目标不可见 | 这篇进了公域 | **主页列表是懒加载分页的**（实证：`matrix_interact._scroll_until_found`，2026-08-01 补量因此实跑失败 5 篇）→ **列表未穷尽即判定不可见**，两篇中任一没被加载进 DOM 都会误判 | 「不可见」只在**列表穷尽**（滚到底或触达轮数上限且无新增卡片）后成立；两篇都要找到才停止滚动 |
| 对照笔记也不可见 | — | — | 判定**探针号/该主页不可信**，本轮弃权不产出结论 + 告警（这也是李牧阳式半死的最早发现手段） |
| 对照笔记指针仍有效 | 它确证公域可见 | 该篇被删除/转私密/被平台收走后，指针指向一个本就不可见的笔记 | 选取时校验 `deleted_at IS NULL AND permission_code=0`；自证连续失败 M 次先换指针再判半死 |
| 曝光为 0 | 平台没分发 | 新笔记 T+1 前曝光天然为 0 | 只作**T+1 之后**的佐证，绝不当首发信号 |
| 删除返回 not_found | 平台已收走这篇（A 型） | 标题匹配不到 ≠ 笔记不存在（同名/改题） | 仅在**同题卡唯一**时采信；同题多篇走 `ambiguous_title` 拒绝 |
| `permission_code=0` | 这篇是公开的 | **已证伪**：台账与平台真值会漂移 | 不作为可见性判据使用，仅用于 KPI 分母 |
| 引用弹窗 toast | 可引用性 | 不代理可见性（2026-08-13 已证伪） | **不用于健康巡检**，仅用于引用功能自身归因 |
| 给旧篇打 `unreachable_at`（退出分母与调度） | 这篇确实永远不可达 | **探针误判**（如懒加载坑的变种）→ 健康笔记被静默剔出分母 | ⚠️ **失效表现是"完成率虚高 + 死笔记计数异常增长"——故障让指标变漂亮，是最危险的反馈方向**。对策：退出分母的笔记必须在 coverage 里**单列可见**（`excluded_unreachable` 计数 + 明细端点），绝不允许只是从分母里消失；该计数异常增长即视为探针误判信号，人工复核 |
| 推送返回 `ok:true` | 老板收到了 | `dedupe_hit:true` 时未必送达（主后端已知 bug：dedupe 落库早于 audience 解析） | `dedupe_hit:true` 视为**未证实送达**，不计成功 |

## 1. 静默失败的两型（实证分类）

| 型 | 形态 | 判别 | 处置 |
|---|---|---|---|
| **A 型「平台收走」** | 管理页无卡、posted 列表消失 | 删除任务报 `note_not_found` | **免删，直接重发**；not_found 不当失败重试 |
| **B 型「留卡不分发」** | 管理页有卡可删、访客不可见、曝光零 | 删除返回 `deleted=1` | **先发后删**（见 §3） |

**重发有效性已实证**（2026-08-14，四篇全线恢复）：高警觉 exp 8→161、讨好的本质 0→192、
讨好型6信号 0→208、凌晨睡不着 1赞→7赞7藏，**A 型与 B 型重发后都恢复正常分发**。
这是「删除重发」这条处置路径的第一份真实背书，也印证了李冠阳天然实验的推论。

探针只能判"访客不可见"，**分不出 A/B**——分型靠删除返回值。样本：号11《凌晨睡不着》= A 型；号1《高警觉》、号8《讨好的本质》《讨好型6信号》= B 型。

**健康笔记的对照指纹**（避免误判，2026-08-13 定标）：互刷 `done/skipped` 且 `not_found=0`、曝光数百以上。真静默失败是互刷 error 14-16 行含 not_found、曝光 0-8。

## 2. 可见性探针（老板「过审才互动」的实现）

### 2.1 流程

**核心设计：同页对照。** 探针打开**目标笔记作者**的主页，在**同一次渲染**里同时找两样东西——待判定的目标笔记，和该作者名下一篇已确证公域可见的**对照笔记**。

```
发布完成 → 延迟 PROBE_DELAY_MIN 分钟 → 探针号 A 打开【作者】主页，同页找两篇：

  对照可见 + 目标可见   → 已进公域 → 放行其余号的全量互动
  对照可见 + 目标不可见 → 目标真的不可见（同页同路径，差异只能来自笔记本身）
                          → 换探针号 B 复探；B 也判不可见 → 记「疑似静默失败」+ 观察队列 + 告警
  对照不可见（无论目标） → 渲染/会话/该主页出问题 → **本轮弃权，不产出任何结论**
                          → 先换对照指针重试一次；仍不可见 → 告警「探针号疑似半死」
```

**为什么必须同页对照，而不是"探针号先自证健康再去看目标"**：李牧阳式半死的症状是「打开**任何发布者主页**都渲染不出笔记卡片」。若对照看的是探针号**自己**的主页/自己的笔记，走的是另一条路径——"自己主页正常、别人主页渲染不出"这种形态完全可能，自证会通过而结论照样错。同页对照把"探针号健康"从**推理**变成**同页比对**，几乎消除代理。

**副产品**：`对照不可见` 这个分支是李牧阳式半死的**最早**发现手段——比 actor 连败熔断更灵敏（后者要撞满 6 次才触发，同页对照第一次就能看出来）。

**探针号 = 首个互动号兼任**，复用 `matrix_interact` 的现有主页定位与滚动能力，零新增浏览器能力，省掉静默失败时其余 7 号的无效会话。

⚠️ **但滚动语义必须改**：现有 `_scroll_until_found` 是「**找到就停**」——目标是新笔记排第 1 位、首屏即命中并立即停止，对照（老笔记，排位靠后）**永远不会被加载**，于是每篇新笔记都落进「对照不可见 → 弃权 + 告警半死」分支，**功能等于没建还天天误报**。探针必须用「**两篇都找到才停**」的循环，且「不可见」只在**列表穷尽**后成立（滚到底或触达轮数上限且无新增卡片）。

### 2.2 对照笔记指针

每个账号维护一个「对照笔记」指针（该号名下最稳的一篇），存 `xhs_accounts.probe_reference_note_id`。

**选取条件**：在满足下列三条的笔记里，**取发布时间最新的那篇**（不是"最稳的老笔记"）——
1. 发布**已过 T+1**（曝光是 T+1 指标，最近一篇的曝光合法为 0，拿它当对照会让自证误报"半死"，故障从"误判笔记"升级成"探针悄无声息整体停摆"）；
2. **台账口径**的健康指纹：`published_notes.views > 0` **且**该篇互刷有成功记录（`done/skipped`）**且** `not_found = 0`。
   ⚠️ **不得用 `note_metrics.exposure` 作判据**——metrics 对部分账号是空的（实测「🤔 好好想想」在 metrics 里 0 篇、台账里 9 篇），用它选对照会把有合格对照的账号误判成"一篇都没有"，直接落进 §2.4 的降级分支。这是"两套宇宙"（台账 vs metrics）的老坑在本设计里的新化身。
3. `deleted_at IS NULL AND permission_code=0`。

**为什么取「合格篇里最新的」而不是「最稳的老篇」**：主页列表按时间倒序 + 懒加载，对照排位越靠后，探针要滚的屏数越多、失败面越大。取最新的合格篇能让**对照与目标落在同一屏或相邻屏**，一次滚动同时命中——这比"加大滚动上限"治本。

**指针失效与轮换**（这本身也是个会失效的代理，必须有可观测的换绑条件）：
- 每次使用前校验条件 3；不满足立即换。
- 对照笔记被淘汰引擎删除、被转私密、或自身变成静默失败 → 条件 1/2 复检时自然淘汰。
- **自证连续失败 M 次（默认 2）先换指针重试，再判探针号半死**——否则一个坏掉的对照会把健康的探针号永久判成半死。

### 2.4 无合格对照时降级放行（fail-open）

**「该账号一篇合格对照都没有」这个分支必须显式存在，且必须 fail-open。** 否则按 §2.1 的逻辑会落到"对照不可见 → 弃权"，而 §2.1 同时是「过审才互动」的闸门，于是：

```
无合格对照 → 探针永远弃权 → 永远不产出"可见"结论 → 永远不放行其余 7 个号
           → 该账号的每一篇新笔记，永久零互动
```

而且它**伪装成另一种故障**——告警说"探针号疑似半死"，排查会朝账号会话方向走，真因却是这个号没有够格的对照笔记。

**降级模式**：
```
合格对照候选数 = 0 →  只找目标笔记本身
                      找到   → 放行互动，结论标 low_confidence
                      找不到 → **也放行**（宁可白跑 7 次会话）
                      ⛔ low_confidence 结论一律不触发破坏性动作
                      + 告警「该账号无合格对照笔记，探针降级运行」
```

**理由是成本不对称，不是"宽松一点没关系"**：

| 误判 | 代价 | 可自愈？ |
|---|---|---|
| 其实不可见却放行 | 7 个号各白跑一次会话 | ✅ 下一轮补量自然重试 |
| 其实可见却不放行 | **该篇永久零互动** | ❌ 没有任何机制会回头补它 |

**谁会命中**（2026-08-13 台账口径实测，各号合格对照候选数）：号7 57 / 号5 47 / 号6 30 / 号8 30 / 号1 27 / 号2 24 / 号10 9 / 号12 7 / **号11 5**——当前**无一为 0**，所以这不是上线首日就命中的问题。但结构性风险真实存在：
- **任何新加入矩阵的账号，头两天必然一篇都不合格**（全没过 T+1），而那正是新号最需要互刷托底的时候；
- 笔记淘汰把老笔记删光、或某号连续几篇低曝光时，同样会掉进来。

### 2.3 确诊与处置门槛

「疑似静默失败」升级为「确诊」需**同时**满足：
- 两个探针号都报不可见（已在 §2.1 内完成）
- **T+1 之后**曝光仍为 0（曝光是 T+1 指标，不可提前采信）

确诊后才进入 §3 的处置。

## 3. 静默失败处置

### 3.1 先发后删（顺序反转，重要）

**机器自动处置一律先发后删**：新篇发布 → 探针确认新篇可见 → 才删旧篇。

理由：李冠阳天然实验证明**旧篇在场不影响新篇分发**（job 68 与 job 77 同内容相隔 4 小时，前者静默死、后者正常分发，且发 77 时 68 的笔记还在）。而先删后发一旦重发卡住（如撞发布冷却），笔记就处于"两头空"——比失败前更糟。人工操作有人盯着可以先删后发，机器不行。

### 3.1.1 🔴 硬前置：note_id 定向删除（本版必须一并实现）

**先发后删与 0.24.3 的 `ambiguous_title` 硬闸语义对撞**，这不是边角问题：

```
1. 用原 payload 发新篇        → 新旧同标题
2. 探针确认新篇可见
3. 删旧篇 → 管理页此刻有两张同题卡 → ambiguous_title 拒绝执行 ⛔
```

先发后删是**故意制造同题双篇**的流程，而同名硬闸的存在就是为了在同题双篇时拒绝删除。若不解决，每处置一次就在账号上留一对重复笔记、白吃一个 100 篇额度，且 `AUTO_REPUBLISH_ENABLED` 一开就成批发生。

**所以 `--note-id` 定向删除是 `AUTO_REPUBLISH_ENABLED=True` 的硬前置，纳入本版实现范围**（此前状态是"需求接受、排期待定"，现在它是阻塞项）。

**实现方向**（择一，实现时验证）：
- 管理页卡片 → 用 posted 接口有序映射定位 → **标题 + 发布时间双交叉校验**后再删（引用弹窗同款技术，但那里的教训是同序假设必须有交叉校验兜底）；
- 或点进笔记详情页从 URL 取 note_id 确认后返回再删（慢但确定）。

**先发后删场景的一个天然简化**：新旧同题且管理页按时间倒序 → **旧篇必排在新篇之后**。可用作定位辅助，但**仍须 note_id 校验**才动手——账号上存在三篇同题（历史遗留）时"删第二张"就不再安全。

**为什么不用"先删后发 + 失败重试"绕过前置**（评估后否决）：那条路今天就能用、不依赖新能力，但有"两头空"窗口（实测《讨好型人格》删后撞发布冷却，等了半小时才发出，期间账号上那篇不存在）。**否决的决定性理由**：空窗期的状态正是"内容已删、访客看不到"——而本系统要解决的就是"访客看不到"。**用一个会制造同类症状的机制去修这个症状，将来排障会自己骗自己。**

### 3.1.2 确诊即退出分母（不等删除成功）

**确诊那一刻就给旧篇打退出标记，而不是等删除落地。** 否则时序上会出现：

```
确诊（两号不可见 + T+1 曝光 0）→ 发新篇（分母 +1）→ 探针确认 → 删旧篇（依赖尚未落地的 note_id 定向删除）
                                    ↑
                       在删除落地前，旧篇一直躺在 coverage 分母里，而它永远拿不到任何互动
```

后果按今天实测的 4-5% 发生率算：**每 100 篇发布沉淀 4-5 篇死笔记 = 32-40 个永不可达的组合**，完成率被一个"系统已经确诊、已经重发、问题实际已解决"的东西按住。这是老板 100% KPI 的直接损失面，而且性质别扭——报表在为已修复的问题扣分。

**字段语义必须与 `deleted_at` 分开**：`deleted_at` = "平台上已经没了"；`unreachable_at` = "确诊不可达，但平台上还在"。确诊时是后者，删除成功后再补前者。**退出分母与退出补量调度都以 `unreachable_at` 为准**，真正的删除是后续清理动作，不该成为报表恢复的前提。

⚠️ **反向风险：退出分母不能变成"扫地毯"**（见 §0 判据表对应行）。退出的笔记必须在 coverage 响应里单列（`excluded_unreachable`），**不许只是从分母里消失**——否则探针误判会让完成率反而更好看，而"故障导致指标变漂亮"是最危险的反馈方向：没人会去排查一个正在变好的指标。

### 3.2 适用范围与终止条件

- **仅对系统发布的笔记自动处置**（有 publish job payload 才拿得到原件）。手工发布的笔记**只告警不自动重发**，显式分支不得静默失败。
- **同一篇内容重发失败 2 次即停止自动重试**，转人工告警。防内容触发的隐性限流把机器拖进死循环（每轮都在烧每号 100 篇的笔记额度）。
- **每次自动删除必须落台账**（不可逆操作没有台账等于没发生过）。

### 3.3 重发前置检查

- **图片体积/格式**：原 payload 若存 PNG 大图（实测 6 张 PNG 共 8.9M 会撞网关），先转 jpg 或复用当时上传成功的图床直链，**绝不原样重放大图**。
- **不带活动挂载**：活动有时效性，过期挂载会毒化发布流。
- 删除走 note_id 定向（现有 `--delete-note` 按标题匹配，同题多篇已由 `ambiguous_title` 硬闸拦住）。

## 4. 告警

### 4.1 A 方案：告警台账（本版自闭环）

新表 `ops_alerts`：`scene / account_id / note_id / title / detail / action_hint / occurred_at / status(open|ack|closed) / dedup_key / created_at`。

- **状态机**：`open → ack → closed`，可标记已处理。**绝不做"每次拉都全量重报"的噪音源**（运营已在别处踩过"把没查到当没有"，不能再造一个反向的噪音坑）。
- **端点**：`GET /api/ops-alerts`（按 status 筛）、`POST /api/ops-alerts/{id}/ack`。
- **coverage 端点响应新增 `excluded_unreachable`**：被 `unreachable_at` 剔出分母的笔记计数 + 明细端点（见 §3.1.2 的反向风险）。运营日报固定盯这个数，**它异常增长就是探针误判的信号**。
- **coverage 端点响应捎带 `alerts_pending` 摘要块**：运营每天拉完成率时顺手看告警，不用记两个端点。详情与标记走独立端点。
- **一律写账号名称，不写账号编号**（老板明确要求）。

### 4.2 B 方案：微信推送（等主后端端点）

**推送能力在 NBDpsy 主后端，nbdpsy-server 绝不自建**（服务号 access_token 单持有方，两边各刷会互顶）。本服务只做"告警的产生、分级、去重、风暴合并、台账、失败透出"，推送是哑管道。

**契约（照主后端现成端点 `POST /api/internal/wechat-notify/v1/send`，不另造）**：
```
X-Signature: sha256=<hex(hmac_sha256(secret, "{timestamp}\n{raw_body}"))>   ← 必须带 sha256= 前缀
X-Timestamp: <unix 秒，±300s 外报 stale_timestamp>
X-Source:    <调用方标识，落 wechat_notify_logs>
body: { audience: "tag:ops_alerts", content: <200 字以内纯文本>, dedupe_key }
```
- ⛔ **签完不许再动 body 字节**（重新格式化、改缩进、调键序都会让签名失效，且报错是 401 而非"body 变了"）。
- **模板只有单字段 `{{content.DATA}}`，上限 200 字**——告警正文按纯文本组织（账号名 + 标题 + 一句 action_hint，超长截断保留"要你做什么"），**不得按六字段模板组织**。
- **收件人用 `tag:ops_alerts` 标签**，不传 openid 列表（对号池会持续新增绑定，按某一刻快照解析会让告警悄悄长成群发）。
- 返回 `dedupe_hit:true` 视为**未证实送达**，不计成功（见 §0 判据表）。

### 4.3 分级

| 事件 | A 台账 | B 推老板微信 |
|---|---|---|
| 探针判定不可见 | ✅ | 连续 N 次不可见才推（需他 App 核实） |
| K 票 not_found | ✅ | ✖ |
| actor 连败熔断 | ✅ | ✅（需他扫码重登） |
| 自动重发触发 | ✅ | ✖ |
| 二次失败转人工 | ✅ | ✖（运营改内容） |
| **探针号疑似半死** | ✅ | ✅（本版新增，与 actor 熔断同类） |

## 5. 配置（全带默认值）

```
PUBLISH_PROBE_ENABLED: bool = True        # 探针总开关
# ⚠️ 成本:探针要真开浏览器,**吃「每号每小时 4 次会话」这条闸**(与补量/发布共享);
#    但**不吃「每号每日 20 篇互动」配额**(那个按 note_interactions 开页篇数算,
#    探针只读不互动不写台账行)。每篇发布约 1-2 次会话(含复探),按每天十几篇发布估,
#    上线后必须实测它对补量产能(~135 组合/天)的挤压;若挤压明显,调大 PROBE_DELAY_MIN
#    或改抽样探测。
PROBE_DELAY_MIN: int = 15                 # 发布后多久开探
PROBE_RETRY_INTERVALS: str = "30,120,360" # 观察队列递增间隔（分钟）
AUTO_REPUBLISH_ENABLED: bool = False      # 自动删重发，默认关
# 🔴 打开前必须先有 note_id 定向删除(见 §3.1.1)。否则先发后删必然卡在 ambiguous_title:
#    新篇发出去、旧篇删不掉,每处置一次留一对重复笔记。**默认关 != 安全** —— 前置没满足
#    就打开它,是成批制造重复笔记,不是"保守地试一下"。
AUTO_REPUBLISH_MAX_ATTEMPTS: int = 2      # 同篇重发失败上限，超过转人工
ALERT_PUSH_ENABLED: bool = False          # B 方案总开关，等密钥到位再开
ALERT_INVISIBLE_PUSH_STREAK: int = 3      # 连续几次不可见才推老板
PROBE_REFERENCE_MIN_EXPOSURE: int = 100   # 对照笔记的曝光下限
PROBE_REFERENCE_RETRY: int = 2            # 自证失败几次后先换对照指针再判半死
```

## 6. 测试要求

- **同页对照四分支**：对照可见+目标可见→放行；对照可见+目标不可见→记疑似（经交叉验证）；对照不可见→**弃权不产出结论**（断言此时既不放行也不记疑似）+ 告警。
- **对照指针轮换**：指针指向的笔记被删/转私密时自动换；自证连续失败先换指针再判半死（断言不会因坏对照把健康探针号判死）。
- **对照选取**：拒绝选中未过 T+1 或曝光为 0 的笔记作对照；在多篇合格时取**最新**那篇（不是最老）。
- **滚动到两篇都命中**：构造「目标在第 1 屏、对照在第 5 屏」的列表，断言探针**持续滚动直到找到对照**，而不是命中目标就停止/弃权。
- **列表穷尽才算不可见**：构造「滚到底仍未见目标」与「未到底就停」两种情形，断言只有前者产出"不可见"结论。
- **交叉验证**：单号说不可见不判定；两号都说才记疑似。
- **无合格对照降级**：合格候选数=0 时断言**放行互动**（不弃权）、结论标 `low_confidence`、发降级告警；且断言 `low_confidence` **不进确诊、不打 `unreachable_at`、不触发删重发**。
- **对照判据用台账不用 metrics**：构造"metrics 为空但台账有合格篇"的账号，断言仍能选出对照（不误落降级分支）。
- **A/B 分型**：删除报 not_found → 走 A 型免删分支且不计失败；deleted=1 → 走 B 型。
- **先发后删**：断言新篇未确认可见前不发起删除；新篇发布失败时旧篇原样保留。
- **验收新篇效果必须按 `publish_time` 认新行，不得按标题取**：重发后新旧同题并存，且 **metrics 视图里已删除的旧行仍在**（2026-08-14 实测：8/6、8/10 两行 exp=0 未随删除消失）。按标题取会命中旧死行、把成功的重发判成"无效"——运营侧已因此差点误判一次。**取新行的判据是 `publish_time` 最新，且必须先刷新 metrics**。
- **删的是旧篇不是新篇**（同题双篇场景）：断言定向删除精确命中旧 note_id、新篇保留。这正是人工操作差点用错工具删掉健康篇的场景，只是这次由机器执行、**没人盯着**。
- **确诊即退出分母**：断言打上 `unreachable_at` 后该篇立即退出 coverage 分母与补量选篇，且**同时出现在 `excluded_unreachable` 计数里**（断言它不是静默消失）。
- **字段语义分离**：断言 `unreachable_at` 不写 `deleted_at`；删除成功后才补 `deleted_at`。
- **前置未满足时的行为**：`AUTO_REPUBLISH_ENABLED=True` 但 note_id 定向删除不可用时，断言**不发起先发后删流程**（宁可不处置，也不制造重复笔记）。
- **终止条件**：同篇第 2 次重发失败后不再自动重试、落转人工告警。
- **手工笔记分支**：无 publish job payload → 只告警不重发（显式断言不进重发路径）。
- **告警状态机**：ack 后不再出现在 pending 摘要；dedup_key 命中不重复建行。
- **推送契约**：签名串格式、`sha256=` 前缀、200 字截断、`dedupe_hit:true` 不计成功。

## 7. 明确不做（YAGNI）

- 不用引用弹窗当可见性探针（toast 语义是可引用性，2026-08-13 已证伪）。
- 不做创作中心「审核中」状态判定（实测《精神内耗》在创作中心显示正常、访客不可见，该状态不可信）。
- 不在 nbdpsy-server 自建微信推送。
- 不做自动内容改写（内容触发的限流由人改，机器只负责发现与告警）。

## 8. 验收

1. 全套 pytest 绿（显式退出码）。
2. 探针在真号跑一轮，对健康笔记判定可见、对已知静默失败笔记判定不可见。
3. 告警台账端点可查可 ack，coverage 捎带摘要正确。
4. `AUTO_REPUBLISH_ENABLED=False` 时确认不发生任何删除。
5. 判据自审表（§0）每一行在代码里都有对应实现与注释。
6. **`PROBE_DELAY_MIN` 必须实测定值**：上线前拿 3-5 篇正常发布，实测「发布完成 → 该篇出现在自己主页」的延迟分布，用 **P95** 定值。在实测完成前，配置注释里标注"**未实测，暂定值**"——偏短会让正常笔记先被判不可见、白跑一轮探针 + 一次误告警。
7. **实测探针对补量产能的挤压**：开探针前后各取一天的组合日增（口径见 `note_interactions` 按日聚合，**不可用 coverage 快照差值**），差值超过 15% 就调参。
