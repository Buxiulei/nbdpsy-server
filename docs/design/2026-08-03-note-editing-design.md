## 一、需求与边界

### 1.1 做什么

对**已发布**的图文笔记,经现有 `POST /api/accounts/{account_id}/note-components` 同一入口:

1. **修改标题**(整体替换);
2. **修改正文**(整体替换);
3. **追加图片**(拼在现有图序末尾);
4. **删除指定图片**(按发布态图序的 1-based 下标);
5. 与既有三组件(合集 / 引用 / 活动)**同一次请求、同一次提交**共存不冲突。

调用方是 nbdpsy-skill 的 REST 客户端,沿用异步 202 + job_id 轮询心智。

### 1.2 明确不做什么(本期边界)

| 不做 | 理由 |
|---|---|
| 图片**重排序** | 需要拖拽拟人化 + 顺序回读校验,风险/收益比差,业务没要 |
| **视频笔记**编辑 | 深链 `noteType=normal` 只对图文验证过;台账 `note_type` 非图文一律 422 拒绝 |
| **清空正文**(content="") | 收益趋零、全量覆盖下风险不明;要清空另立需求 |
| **删光全部图片** | 图文笔记 0 图状态未知且不可逆;强制校验"删除后原图剩余 ≥1"(不允许拿新增图凑数,见 3.2) |
| 话题实体**保全/重建** | 正文替换会丢既有话题实体(chip),本期**如实上报 `topics_dropped`**,不做下拉重选流重建(那是 step6 级别的独立工程);调用方要保话题就把话题文本以外的方式自行处理——见 6.3 风险披露 |
| 封面指定、位置、商品、@人 | 业务没要 |
| 发布新笔记路径的文本/图片 | `atomic_tasks` 已有,不动 |
| published_notes 以外的台账联动(如 content_archive) | 归档副本语义是"发布时刻的快照",不追改 |

### 1.3 继承的硬约束(每条都有事故背书,一条不减)

- 全程 `SyncHumanActions` 拟人化;`page.evaluate` **只读**;**绝不构造平台请求**(提交是全量覆盖语义,漏 `privacy_info` 可能把私密变公开——三组件设计 2.3/2.4);
- **权限保全**:提交前后各读一次权限档位,不符中止/改回(三组件设计 3.4,原样复用);
- "没报错"不当成功凭据:每步当场回读 + 提交后重进页面逐项回读(静默失败是这条产品线的常态);
- **非幂等**,kind 不进 `_IDEMPOTENT_KINDS`(kind 不变,天然满足);
- 任何页面结构假设,写代码前必须有真号采集的夹具背书(第五节 HARD-GATE)。

## 二、方案对比与裁决

### 方案 A:扩展现有 `note_components` kind(调研报告第 6 节倾向)

REST 请求体加可选字段(title / content / add_images / remove_image_indexes),浏览器层在
`set_note_components` 既有骨架(进更新页 → 权限留底 → apply → 提交前复读权限 → 点发布 →
重进回读)的 apply 阶段插入文本/图片步骤。一次请求一次提交。

- 优点:
  1. **一次请求只有一次全量覆盖提交**。提交次数就是风险次数——文本+图片+组件混合请求下,
     方案 B 至少两次提交,风险直接翻倍;
  2. 权限保全 / 三态回读 / 静默失败纪律 / 号锁+浏览器闸+SyncClient 生命周期 / job 台账全部
     原地复用,零复制;
  3. "至少给一个"校验、非幂等语义、轮询契约(applied/failed 三态)自然扩展;
  4. 满足业务硬性要求"与三组件同一入口"。
- 缺点:
  1. `note_components` 这个名字对"改标题正文"语义已经名不副实;
  2. `note_components.py` 已 1541 行,继续堆会失控;
  3. apply 阶段步骤增多,失败语义要重新想清楚(见 4.4:文本/图片是"破坏性编辑步",
     失败语义必须比组件更严)。

### 方案 B:新 kind `note_edit` + 独立浏览器模块,共享入口

REST 同一 POST 端点,但内部按字段拆两条 job(`note_components` / `note_edit`),各自独立
"进页→改→提交→回读"。

- 优点:模块边界干净,`note_components.py` 不再膨胀;两条产品线独立演进。
- 缺点:
  1. **混合请求要提交两次**,每次都是全量覆盖——第二次提交时第一次的结果又被整体重写一遍,
     两次窗口之间平台侧任何变化都会被覆盖,这是把最危险的语义主动翻倍;
  2. 权限保全 / 回读 / 提交骨架要么复制一份要么抽公共层——抽公共层就是动
     `set_note_components` 真号验证过的主路径,与"红质心故意各写一份"(代码注释明示的
     取舍)同理,风险高于收益;
  3. 调用方要理解"一个请求可能出两个 job_id"或"字段组合决定走哪条 kind",契约复杂化;
  4. 台账里同一篇笔记两条 kind 交错,事后审计"当时改了什么"要跨 kind 拼。

### 裁决:方案 A,附一条结构性修正

**同意调研报告第 6 节的倾向,理由以"提交次数 = 风险次数"为首。** 全量覆盖语义下,
把文本/图片与组件拆成两条提交路径不是解耦,是把同一颗雷埋两处。

**修正**:同意"不开新 kind",但**不同意继续往 `note_components.py` 里堆代码**。新增浏览器
逻辑放独立新文件 `app/browser/note_editing.py`(文本替换 + 图片增删的 apply 步骤与逐步
回读,纯函数式,吃 page/human/responses 入参),由 `set_note_components` 在 apply 阶段
编排调用。kind 不变、REST 端点不变、提交/权限/回读骨架不变;`note_components.py` 只在
编排点(`set_note_components` / `apply_components` 调用序列、`_verify_after_submit`、
`_compose`)做手术式扩展。这样"单一提交路径"与"文件不失控"两头都拿到。

## 三、REST 契约

### 3.1 请求体扩展(`POST /api/accounts/{account_id}/note-components`)

在现有 `NoteComponentsRequest` 上加可选字段(现有字段与语义一字不动):

| 字段 | 类型 | 校验 | 语义 |
|---|---|---|---|
| `title` | `str \| None` | 显示长度 ≤20(复用发布链路的 `get_display_length` 同款算法);允许空串 `""`=清空标题(平台侧 `title:""` 是合法显式值,三组件设计 2.3 实证);超长 **422,绝不静默截断**(编辑场景调用方给的是精确意图,截断=改错) | 整体替换标题;`None`=不改 |
| `content` | `str \| None` | `min_length=1`;长度 ≤ 发布链路同款 `XHS_MAX_BODY_LENGTH`(900,给活动话题注入留余量);超长 422 | 整体替换正文;`None`=不改;不支持清空(见 1.2) |
| `add_images` | `list \| None` | 1-18 项;每项三形态之一(URL / base64 / 服务端本地路径),**复用发布链路 `materialize_images` 落盘机制**;`expected_image_count + len(add_images) - len(remove_image_indexes) ≤ 18` | 追加到现有图序末尾 |
| `remove_image_indexes` | `list[int] \| None` | 1-based、去重、每项 `1 ≤ i ≤ expected_image_count`;**`expected_image_count - len(remove) ≥ 1`**(不许拿新增图凑最低数——新增可能失败,失败后就是删光) | 删除指定位置的图,下标按**发布态图序** |
| `expected_image_count` | `int \| None` | 给了 `add_images` 或 `remove_image_indexes` 时**必填**,1-18 | 调用方声明"我认为这篇现在有几张图"。浏览器层实数不符 → 图片操作整体拒绝(见 4.4)。这是删除类操作的第一道防呆:台账认知过期时零点击退出 |

"至少给一个"校验扩展为:`collection_id / quoted_note_id / activity_id / related_counselor /
title / content / add_images / remove_image_indexes` 全空 → 422(现有 validator 加枚举项)。
注意 `title=""` 是"给了"(清空标题是明确意图),用 `None` 与 `""` 区分。

服务层前置校验(建 job 前,`start_note_components_endpoint` 内):

- 台账查这篇 `published_notes`:不存在该 `note_id` → 404;`note_type` 非图文 → 422;
- `add_images` 在**建 job 前**先 materialize 落盘,坏图 / 拉不下来 → 422(别让它排队两分钟
  后才在浏览器层失败——与"入口拦无意义提交"同一纪律)。

### 3.2 轮询返回扩展(`GET /api/note-components/{job_id}`)

`applied` 字典在现有 `collection / quote / activity` 之外按请求新增键,三态语义不变
(`true`=回读确认生效 / `false`=回读确认没生效 / `null`=没能回读):

| 键 | 生效判据(提交后重进页面回读) |
|---|---|
| `title` | 回读标题归一后 == 目标标题 |
| `content` | 回读正文归一后**以目标正文开头**(活动步会往末尾追加话题,不能用全等) |
| `image_add` | 回读图数 == 留底图数 - 实删数 + 追加数 |
| `image_remove` | 同上(同一条计数等式,两键分别报告以便调用方定位是哪半失败) |

新增结果键:

- `topics_dropped: list[str]`:正文替换前旧正文里的话题实体名(`extract_topics(body_before)`),
  替换即丢失,如实上报;
- `images_before / images_after: int`:留底与回读的图数;
- `ledger_synced: bool`:台账回写结果(见 3.3);
- `aborted_before_submit: bool`:破坏性编辑步失败导致放弃提交(见 4.4)时为 true——
  此时**笔记原样未动**,调用方可安全重试;这是与"提交了但部分生效"完全不同的状态,
  必须让调用方一眼分清。

`failed` 数组、`result_status`(done / partially_applied)、error 时也下发逐项详情等
既有语义全部不变。MANIFEST_ENTRIES 同步更新(字段、错误码、四条硬约束注记加上
"正文替换会丢既有话题实体"与 `aborted_before_submit` 说明)。

### 3.3 台账回写(published_notes.title 过期问题)

**修正调研报告一处过时结论**:`published_notes` **有** `content_text` / `content_fetched_at`
列(模型 `app/models/published_note.py:93-96`),"无 content_text 字段"是旧信息。故回写
不需要任何迁移:

- 时机:服务层 `execute()` 拿到浏览器层结果后、返回前;
- 条件:仅当对应项回读确认生效(`applied.title is True` → 回写 `title`;
  `applied.content is True` → 回写 `content_text` + `content_fetched_at=now`);
- **回写值用提交后回读的平台真值**(不是请求值):平台可能有服务端改写,回读值才是真相
  ——与 `read_note_title` docstring"平台当前标题比台账权威"同一世界观;
- 回写失败只记日志 + `ledger_synced=false`,不改变 job 结果(台账最终一致由既有
  note 同步链路兜底);
- 图片增删不回写(台账不存图列表,无可写字段)。

### 4.1 文本输入的实现方式

`atomic_tasks._type_into_robust` **不能直接调用**(绑死 `XHSPublishFlow` 实例:
`self.page / self.human / self._take_screenshot / self.current_step`)。在
`note_editing.py` **仿写**一个模块级 `_type_into(page, human, selectors, value,
*, clear_first)`:

- 照抄其三条实测纪律:只读 JS 取坐标不持 ElementHandle(React 聚焦重渲染句柄脱离)、
  拟人坐标点击聚焦、`human.type_text` 逐字输入;
- `clear_first=True` 时先 `Ctrl+A → Backspace`(发布页重试清残留的同款手法,但在编辑
  场景**首次就要清**——框里是旧内容);
- 选择器:标题 `_TITLE_INPUT`(夹具实证更新页唯一命中、可见、value 可读),正文写入用
  `div.tiptap.ProseMirror[contenteditable='true']`(夹具实证唯一命中),读回沿用现有
  `_BODY_TEXT_JS`。定位已闭环;**写入行为**(清空是否干净、话题 chip 是否被 Ctrl+A
  连带删除、输入是否触发校验)从未验证,属 [G3] 范围;
- 输入后当场读回(`read_note_title` / `read_body_text`)全等校验,不等 → 该步 error。

**不抽公共函数改 `atomic_tasks`**:那是真号验证过的发布主路径,与红质心"故意各写一份"
同一取舍。两份实现的坑注释互相引用,防将来只修一边。

### 4.2 步骤顺序的三条理由

1. **正文在活动之前**:活动把话题追加到正文末尾(三组件设计 2.7①);若正文替换在活动
   之后,`Ctrl+A` 会把刚注入的话题实体一并清掉,活动白设还丢话题。先文后活动,注入
   落在最终正文末尾,`appended_part` 差值统计照常成立;
2. **图片在文本之前**:图片操作失败概率最高(证据最少),放最前让"失败即弃提交"
   尽早发生,少做无用功;
3. **删除在追加之前**:remove 下标语义锚定"发布态图序",追加只拼末尾不动 1..n 位,
   但先删后加让"剩余 ≥1"校验始终以原图计,语义最简。

### 4.3 图片删除的红线适配

现行模块红线是"绝不点删除类按钮"(合集 `.close-icon`、「取消关联」、笔记删除)。本功能
**必须点图片删除按钮**,红线按以下方式收窄而非废除:

- 原红线三项**原样保留**,一个都不解禁;
- 图片删除按钮 `.close-btn.hoverShow` 是**新增的受控例外**,前提全部满足才允许点:
  1. 选择器已有真号夹具背书(附录 A:与 .img-container 1:1、各 20x20、hover 显形),
     绝不按文案/位置猜;
  2. `expected_image_count` 闸已通过(③),且目标容器的**序号文本**与要删的下标一致
     (夹具实证容器 text 就是 "1".."N",这是删除前最后一道身份复核);
  3. 每次点击前用只读 JS 确认落点元素就是目标图容器内的删除控件(与 `click_publish`
     的 `elementFromPoint` 复核同款纪律);
  4. 点后当场数容器,-1 不成立 → 重试同一张封顶 3 次(窄按钮静默失效的活动先例),
     仍不成立 → 立刻停手,不再点下一张,整 job 走弃提交路径。
- **安全兜底是"未提交不落库"**:编辑器内删图只是前端态([G2] 必须实证),放弃提交
  离开页面即恢复原状。真正不可逆的只有⑧那一次点击——所以一切"不确定"都在⑥被拦下。
- 若有确认弹窗([G2] 待查):弹窗按钮按文案精确匹配,处理完必须确认弹窗已关
  (引用弹窗盖发布按钮致三连误诊的事故教训,收尾进 finally)。

### 4.4 失败语义:破坏性编辑步与组件步不同

现行纪律"单项失败不阻断其余项、部分成也提交"对组件成立——组件失败=没设上,原内容
无损。**文本/图片不满足这个前提**:标题清空到一半、图删了一张卡住,此时提交=把残缺态
真发布出去。故:

- **组件步**(合集/引用/活动):维持现状,单项失败不阻断,部分成也提交;
- **破坏性编辑步**(④a-④d):**任一失败 → 放弃提交,整 job error,
  `aborted_before_submit=true`**。编辑器态不落库,笔记原样未动,调用方可安全重试;
- 混合请求下组件已在编辑器内设好但因④失败弃提交:组件设置一并丢弃(不落库无副作用),
  结果里逐项如实报"编辑器内已设但未提交"。

### 6.2 回滚

- **代码回滚**:纯增量(新文件 + 现有文件手术式扩展 + REST 可选字段),无 DB 迁移
  (`content_text` 列已存在);回滚 = 恢复旧版本代码,旧客户端请求体不受影响
  (新字段全可选,老请求语义零变化);
- **运行时回滚(单次任务)**:提交前任何失败 → 弃提交,笔记原样;提交后发现权限被改 →
  现有 `_restore_permission` 改回;提交后发现内容改错 → **无自动回滚**(再提交一次
  又是全量覆盖),结果里 `applied` 逐项真值 + 台账留 payload,人工按记录改回——
  这与三组件现状一致,MANIFEST 已警示"看到 error/unknown 先核对当前状态再决定"。

### 6.3 需要向调用方书面披露的行为

写进 MANIFEST notes(调用方唯一会读的地方):① 正文替换丢话题实体(`topics_dropped`);
② `aborted_before_submit=true` 时笔记原样未动、可安全重试,其余失败必须先人工核对;
③ 图序下标以发布态为准,`expected_image_count` 对不上整个图片操作拒绝;④ 台账
title/content_text 在成功后自动回写。

1. 只改标题 → 回读全等 + `published_notes.title` 已更新;
2. 只改正文(带旧话题的笔记)→ 回读前缀成立 + `topics_dropped` 正确 + `content_text` 回写;

6. 失败注入:mid-way 断点(如 remove 指向不存在下标)→ `aborted_before_submit=true`
   + 重进页面笔记原样。
