# 历史笔记互动补量(点赞 / 收藏)设计

日期:2026-08-02
状态:待实现

## 一、需求

1. **自动**:每日笔记数据更新后,发现**手工新增的笔记**(orphan),自动触发互动任务
   (点赞 + 收藏);
2. **评论保持现状**:只有本系统发布的笔记才自动触发评论,手工笔记不评论;
3. **手工批量**:支持给某个账号的历史笔记互动、给所有账号的历史笔记互动、
   以及**某个新加入的账号给其余所有账号的历史笔记互动**(新号补历史)。

## 二、规模与风险(先算清楚再设计)

台账现状(2026-08-02,账号 8/9 尚未同步,实际更大):

| 账号 | 台账篇数 | 其中公开 |
|---|---|---|
| 1 我们都有病 | 40 | 12 |
| 2 聊心理 | 30 | 30 |
| 5 聊创伤 | 21 | 20 |
| 6 亲密关系 | 20 | 19 |
| 7 NBDpsy | 61 | 58 |
| **合计** | **172** | **139** |

**全矩阵互补一遍 ≈ 139 × 6 = 834 次互动,按 40 秒/次算约 9.3 小时纯浏览器时间。**

而这 834 次全是**对老笔记的集中互动**——平台眼里最典型的补量特征,风险显著高于
"新笔记发布后互动"。参考:今天已有两个账号因访问频次被弹扫码验证墙,
而那只是**一小时 5 次会话**的量级。

**所以本功能的设计核心不是"能不能做",是"怎么摊开做而不把号打挂"。**

## 三、设计

### 3.1 互动台账(新表 `note_interactions`)

没有它就无法做增量——每次都得开笔记页才知道有没有点过,而"开页"本身就是最贵的动作。

```
id
actor_account_id     谁去互动的
note_id              互动的哪篇
action               like / collect
status               done / skipped(平台上已是目标态)/ error
detail               失败原因
done_at
唯一约束 (actor_account_id, note_id, action)
```

**平台状态仍是正确性的唯一来源**——`_icon_action` 读 `use[xlink:href]` 判断
`#like`/`#liked`,已是目标态就 `skipped` 不重复点(重复点 = 取消赞)。
本表只用于**跳过已处理项、避免白开浏览器**,不作为正确性依据。

### 3.2 三条触发路径

**A. 自动:每日同步发现手工新增笔记**

台账同步(T2)新建 `orphan` 行时,除已有的核心目的回填外,再登记一条互动任务:
让矩阵内其余账号对这篇新发现的笔记点赞收藏。

**不触发评论**——评论只在本系统发布时触发(需求第 2 条)。

**B. 手工:指定范围批量补量**

```
POST /api/interaction-backfills → 202 {job_id}
  scope:
    "account"       给某账号的历史笔记互动(由其余矩阵号来做)
    "all"           给所有账号的历史笔记互动
    "newcomer"      某新号去给其余所有账号的历史笔记互动
  target_account_id   scope=account 时:被互动的账号
  actor_account_id    scope=newcomer 时:新加入的那个号
  limit               本次最多做多少(不传用默认日上限)
GET /api/interaction-backfills/{job_id}
```

**C. 已有的发布后矩阵互动**不变。

### 3.3 节流(本设计的核心)

四层闸,缺一不可:

1. **日上限**:每个 actor 账号每天最多互动 N 篇(默认 20,可配置)。
   834 次全量补完 ≈ 7 个号 × 20/天 ≈ 6 天,这是**刻意的**;
2. **单轮上限**:一次任务最多处理 M 篇(默认 5),超出的留给下一轮;
3. **间隔抖动**:两篇之间 `random.uniform(60, 240)` 秒。**绝不连续快跑**;
4. **共用 `browser_slot`**:不额外起并发,与其它浏览器任务排队。

**优先级**:新发现的笔记 > 最近发布的 > 更早的。老的个人生活向内容优先级最低。

### 3.4 只互动公开笔记

`permission_code == 0` 才做。私密笔记访客根本看不到,点赞收藏无从谈起;
**`null`(未知)同样不做**——不确定就不碰。

### 3.5 定位:优先 note_id

有 `note_id` 就用它(台账现在都有);标题只在无 id 时兜底。
台账 title 会过期(实测平台改过标题而台账未同步),靠标题会失配。

### 3.6 撞墙即停

任何一篇互动时 `page.url` 出现 `captcha` / `website-login`:

- **立刻中止本轮**,不再处理剩余篇目;
- 该 actor 账号置 `cookie_status='restricted'` 并落 `risk_events`;
- 已完成的部分照常记账,不回滚。

这是唯一比"做完"更重要的事。

## 四、非幂等性

`interaction_backfill` **非幂等,不进 `_IDEMPOTENT_KINDS`**:僵死重跑会对同一批笔记
重复处理。虽然 `_icon_action` 在平台侧会 `skipped` 不重复点,但重跑仍会白开浏览器、
消耗当日配额、增加风控暴露。

## 五、验收

1. 单元测试:日上限与单轮上限生效、已互动的跳过不开浏览器、私密与 `null` 被排除、
   撞墙立刻中止且已完成部分保留、间隔抖动落在区间内、三种 scope 的选篇正确、
   `interaction_backfill` 未进 `_IDEMPOTENT_KINDS`;
2. 真号验收由我做,**首次只跑 limit=2 探路**,确认无异常再放开。

## 六、必须向用户说明的取舍

全量补完需要约 6 天(按日上限 20/账号)。**这是设计意图不是性能问题**——
一口气刷完 834 次几乎必然触发风控,而账号被挂墙的代价(需人工扫码、期间所有任务失败)
远高于"慢几天"。

若业务上确实需要更快,可调高日上限,但**风险由业务侧承担**,且建议先小批量试跑观察。
